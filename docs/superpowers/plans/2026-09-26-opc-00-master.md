# opc — Plano de Implementação Mestre

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar o plugin Claude Code `opc`, que controla o OpenCode (paridade com o codex-plugin-cc + integração máxima, swarm, conclave e MCP), fase a fase, cada uma com portão de testes e validação ao vivo.

**Architecture:** O plugin sobe e gerencia um `opencode serve` por workspace e conversa com ele por HTTP + SSE (API v1). Uma CLI única (`opc` → `opc-companion.mjs`) atende slash commands, hooks, reaper, assistente de terminal e (na F5) um servidor MCP. Os módulos de `lib/` têm uma responsabilidade cada e se comunicam pelas interfaces congeladas neste documento.

**Tech Stack:** Node.js ≥ 20 (ESM `.mjs`, `fetch` nativo, `node:test`), zero dependências de runtime, OpenCode 1.18.32, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-25-opc-plugin-design.md` (rev. 3). O plano argumenta a partir da spec; quem executa lê os dois.

## Global Constraints

- Node ≥ 20 (`engines: {"node": ">=20"}`); checagem em runtime com mensagem clara; CI em Node 20 e 22.
- Zero dependências de runtime. `devDependencies` também vazias (nada de `npm install`).
- Código, identificadores, mensagens de commit e nomes de arquivo em inglês. Docs e textos voltados ao usuário em PT-BR.
- OpenCode mínimo `1.18.0`; alvo testado `1.18.32`; só a API v1 (`/session/*`, `/event`, …), nunca `/api/*`.
- Servidor sempre em `127.0.0.1`, porta escolhida pelo plugin e autenticado com `OPENCODE_SERVER_PASSWORD` (usuário `opencode`).
- A senha do servidor e as chaves de provider nunca aparecem em stdout, stderr, logs, docs ou fixtures commitadas.
- O plugin nunca escreve em `~/.config/opencode/` nem no `auth.json` do OpenCode.
- Nenhum sinal para um processo cuja identidade (cmdline + start time) não confira.
- Diretórios de estado com modo 700 e arquivos com modo 600.
- `always` nunca é enviado em `permission reply`.
- Exit codes conforme a spec, §4.1: `0, 2, 3, 4, 5, 6, 7, 130`.
- Namespace de comandos `/opc:`; executável `opc`; título das sessões com o prefixo `OPC: `.
- Testes ao vivo só com `OPC_LIVE=1`, nunca no CI, sempre em diretório descartável; modelos `omniroute-personal/opencode-go/{deepseek-v4.1-flash,qwen3.8-max,kimi-k3}`.
- Licença Apache-2.0; `NOTICE` credita o `openai/codex-plugin-cc`; nada copiado do `swarm-code-plugin`.

## Review Focus

Entradas e condições que a spec implica e que mais provavelmente quebram o uso real. Cada
linha tem teste na tarefa dona, indicada entre colchetes.

1. **Prompts com aspas, crases, `$()`, quebras de linha e unicode** passam intactos até o
   OpenCode e nunca são expandidos pelo shell. [F0 · args / F2a · task, teste `prompt-roundtrip`]
2. **Workspace sem git ou fora de repositório**, e caminho com espaços ou acentos: estado,
   hash e `directory` corretos. [F0 · state, teste `workspace-with-spaces`]
3. **Primeiro uso sem config nenhuma** (sem `config.json`, sem `.opc.json`): comandos de
   descoberta e `task` funcionam com o default do OpenCode, ou erram de forma clara (exit 4
   ou 2), nunca com stack trace. [F1 · config, teste `no-config-first-run`]
4. **Servidor morto entre dois comandos** (`kill -9` manual, reboot): o próximo comando
   detecta, limpa o registro e sobe outro, sem pendurar. [F0 · server, teste `server-killed-externally`]
5. **Saídas grandes** (resposta de modelo com mais de 1 MB, diff enorme, log de job longo):
   não estouram memória, respeitam os limites de 5 MB de log e 400 KB de diff inline e
   continuam renderizando. [F2a · runner/jobs, teste `large-output`; F2b · git, teste `huge-diff`]

### Teardown (padrão único)

`testEnv`/`makeWorkspace` registram env e workspace numa limpeza por teste com **um só** `t.after` (F0), que roda, em ordem: `registerStopper`s (ordem inversa) → `stopAllServers(env, ws)` para cada par env × workspace → remoção dos temporários. O `node:test` roda os `t.after` em ordem de registro (FIFO, conferido no Node 22), então:

- **Nunca** `t.after(() => stopAllServers(...))` nem `t.after(() => runCli(...))` depois de `testEnv`/`makeWorkspace` (rodaria depois da remoção dos diretórios → `ENOENT` e servidor órfão).
- Precisa rodar antes de parar os servidores (cancelar job, soltar lock, matar filho no workspace, fechar cliente MCP) → `registerStopper(t, fn)`.
- Env montado à mão (testes ao vivo) → `trackEnv(t, env)`; diretório de dados próprio → `trackTempDir(t, makeTempDir('opc-…'))`; servidor num diretório que não veio do `makeWorkspace` → `trackWorkspace(t, dir)`. Nunca copiar o env (`{ ...testEnv(t), … }`): use `testEnv(t, { extra })`.
- `t.after` direto só para recursos independentes dos temporários (`AbortController`, `prompter.close()`, `fake.close()` de fake em processo — em modo attach ele precisa continuar de pé durante o `stopAllServers`).
- Exceção aceita: teste ao vivo autocontido, sem os helpers de registro, que num único `t.after` para o servidor e só depois remove os próprios diretórios (F1 ao vivo, `_f2b-live-helpers`, F5 ao vivo).

### Contrato (`tests/live/contract.mjs`, F0 — único executor, roda em todo portão)

`PROBES` (`{ name, method: 'GET', path, used, optionalUsed? }`), `EVENT_TYPES` e `MAP_PATHS` moram em `tests/fixtures/contract-shapes.mjs` (registro). Fase que passa a depender de um endpoint GET ou evento passivo acrescenta a entrada ali por passo "Modify" explícito (F1: `/provider`, `/command`, `/skill` + `MAP_PATHS` dos mapas de IDs). Formas que só existem com sessão/turno reais ficam em testes ao vivo da fase, sem o nome "contract" (`f1-fixture-coverage.mjs`: cobertura das fixtures; `f3-session-shapes.mjs`: fork/revert/summarize).

### Testes ao vivo (`tests/live/`)

- **Guarda:** `skip` quando `process.env.OPC_LIVE !== '1'` (scripts `probe-*` saem com aviso).
- **Modelo:** `process.env.OPC_LIVE_MODEL ?? 'omniroute-personal/opencode-go/deepseek-v4.1-flash'` (cada fase pode fixar o seu).
- **Ambiente:** workspace e `OPC_DATA_DIR` descartáveis; servidor encerrado pela limpeza da F0 (`trackEnv`/`trackTempDir`) ou pelo `t.after` único autocontido.
- **Registro:** a saída vai para `docs/phases/F<n>-report.md` (redigida).

## Regras de git (execução)

Aplicam-se a toda fase (regras do operador, §2.3 e §2.5):

1. **Autorização:** commit, push, PR e merge só com autorização explícita do operador na sessão de execução. Se ela não existir, pedir antes do primeiro commit da fase.
2. **Branch:** `feat/opc-<fase>` a partir da `main` (ex.: `feat/opc-f0`). Um PR por fase, com o relatório de fase no corpo. Merge só depois de avisar o operador.
3. **Commits:** Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`, `refactor:`), curtos e coerentes com o diff.
4. **Sem atribuição de agente:** nada de `Co-Authored-By`, `Signed-off-by` ou "Generated with". Reler a mensagem antes de cada `git commit`.
5. **Primeiro commit** (antes da F0, na `main`, com autorização): `docs: add opc design spec and implementation plans`, com a spec e estes planos.
6. **Nada de** `--no-verify`, `push --force` ou `reset --hard`.
